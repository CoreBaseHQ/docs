---
title: "Flows"
description: "Chain agent and action steps into a multi-step DAG — each step receives the output of the steps before it, branches fan out, and execution is durable."
---

A flow is more than one step. You connect nodes with edges, and CoreBase executes them as a **directed graph (DAG)**: it follows the edges in topological order, runs each agent and action node, and passes every node the output of the steps that feed into it.

## How execution works

1. The flow loads its graph (nodes + edges).
2. Nodes are ordered **topologically** from the edges — upstream before downstream. (No edges? It falls back to the order you placed them, so simple linear flows just work.)
3. Each **agent** and **action** node runs in turn. Trigger nodes define *when*, so they aren't executed as steps.
4. Each node receives the **combined output of its upstream nodes** as context, so step B can build on step A's result.
5. The run record collects every step's output.

```
[ Trigger ] → [ Agent A: pull overdue invoices ] → [ Agent B: draft a chase email per invoice ]
                                                  ↘ [ Action: summarize totals for the manager ]
```

Here A runs first; B and the action both receive A's output and run as a fan-out branch.

## Chaining context

Whatever an upstream node produces is prepended to the downstream node's instruction as context. So you can keep each step focused:

- **Agent A** — *"List customers whose contract renews in the next 30 days."*
- **Agent B** (fed by A) — *"For each customer above, check open support tickets and flag churn risk."*

B doesn't need to re-derive A's list; it's handed to it.

## Agent vs. action nodes

| Node | Use it for |
|---|---|
| **Agent** | Open-ended reasoning with its own instruction and source scope. |
| **Action** | A fixed, single-purpose step described in one line. Runs as an agent step using that description. |

Both execute the same way and both receive upstream context. Use **action** when the step is a fixed task; use **agent** when you want to give it more instruction and its own source scope.

## Durability

Flows run on durable execution, which means:

- A step that fails is **retried** before the run is marked failed.
- A long-running flow doesn't hold an HTTP request open — it runs in the background.
- A restart mid-run doesn't lose progress.

## Good to know

<Note>
  Branches **fan out** (multiple downstream nodes from one node all run). Conditional branching ("only run B if A found something") and per-node step logs are on the roadmap — today every executable node on the path runs, and the run record shows the combined output.
</Note>

A cycle in the graph won't hang the run — CoreBase detects it and runs the remaining nodes in their original order as a fallback. Keep flows acyclic for predictable ordering.
