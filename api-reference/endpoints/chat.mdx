---
title: "Create a chat completion"
openapi: "api-reference/openapi.json POST /api/v1/chat/completions"

The endpoint is OpenAI-compatible — point any OpenAI SDK at `https://api.corebasehq.com/api/v1` and it just works. By default responses stream as `text/event-stream` using the standard `chat.completion.chunk` payload, terminated by `data: [DONE]`; set `stream: false` to get one complete `chat.completion` JSON object instead (for workflow tools like n8n or Zapier, and plain HTTP calls).

<Note>
  `POST /api/v1/chat/completions` is the canonical path. The older `POST /api/v1/chat` is kept as an alias for backward compatibility and behaves identically.
</Note>

<Note>
  The endpoint is **stateless by default** — pass the full history on every
  call, exactly like OpenAI. To skip resending history, take the
  `conversation_id` from a previous response and send only the new message —
  see [Multi-turn](#multi-turn).
</Note>

## Streaming response

`Content-Type: text/event-stream`. Each frame is a standard OpenAI `chat.completion.chunk`:

```
data: {"id":"chatcmpl-abc123","object":"chat.completion.chunk","created":1716284400,"model":"anthropic/claude-3-5-sonnet-20241022","choices":[{"index":0,"delta":{"role":"assistant","content":""},"finish_reason":null}]}

data: {"id":"chatcmpl-abc123","object":"chat.completion.chunk","created":1716284400,"model":"anthropic/claude-3-5-sonnet-20241022","choices":[{"index":0,"delta":{"content":"Top "},"finish_reason":null}]}

...

data: {"id":"chatcmpl-abc123","object":"chat.completion.chunk","created":1716284400,"model":"anthropic/claude-3-5-sonnet-20241022","choices":[{"index":0,"delta":{},"finish_reason":"stop"}]}

data: [DONE]
```

Every response also carries an `X-Conversation-Id` header — keep it to continue the conversation later without resending history.

## Non-streaming (`stream: false`)

One complete `chat.completion` object, `Content-Type: application/json`:

```json
{
  "id": "chatcmpl-abc123",
  "object": "chat.completion",
  "created": 1716284400,
  "model": "corebase",
  "conversation_id": "abc123",
  "choices": [
    {
      "index": 0,
      "message": { "role": "assistant", "content": "Your top customers are…" },
      "finish_reason": "stop"
    }
  ]
}
```

The agent still queries your sources server-side — the request simply blocks until the full answer is ready, so expect response times of several seconds for tool-heavy questions. `conversation_id` is a CoreBase extension; OpenAI clients ignore it.

## Using the OpenAI SDK

Because the wire format matches OpenAI, you can use any OpenAI client:

```python
from openai import OpenAI

client = OpenAI(
    api_key="cb_live_xxx",
    base_url="https://api.corebasehq.com/api/v1",
)

stream = client.chat.completions.create(
    model="corebase",
    messages=[{"role": "user", "content": "Top 3 customers by revenue this quarter?"}],
    stream=True,
)

for chunk in stream:
    delta = chunk.choices[0].delta
    if delta.content:
        print(delta.content, end="", flush=True)
```

```ts
import OpenAI from "openai";

const client = new OpenAI({
  apiKey: process.env.CB_LIVE!,
  baseURL: "https://api.corebasehq.com/api/v1",
});

const stream = await client.chat.completions.create({
  model: "corebase",
  messages: [{ role: "user", content: "Top 3 customers by revenue this quarter?" }],
  stream: true,
});

for await (const chunk of stream) {
  process.stdout.write(chunk.choices[0].delta.content ?? "");
}
```

## Tool calls

When the model invokes one of your connected data sources, the call streams as a standard OpenAI `tool_calls` delta:

```json
{
  "choices": [{
    "index": 0,
    "delta": {
      "tool_calls": [{
        "index": 0,
        "id": "call_abc",
        "type": "function",
        "function": {
          "name": "erp_prod__execute_query",
          "arguments": "{\"sql\":\"SELECT TOP 3 ...\"}"
        }
      }]
    },
    "finish_reason": null
  }]
}
```

Tool execution happens server-side inside CoreBase — you don't need to handle the call. The next text deltas after the tool call carry the model's interpretation of the result.

## Errors

| Status | Meaning |
|---|---|
| `400` | Body schema invalid |
| `401` | Missing or invalid token — see [Authentication](/api-reference/authentication#errors) |
| `403` | Token lacks `mcp_query` permission |
| `404` | Unknown `project_id`, or a `conversation_id` that doesn't belong to this token |
| `409` | No LLM provider key configured for the organization — set one in [Settings → LLM keys](/platform/llm-keys) |
| `429` | Rate limit hit. Honor `Retry-After`. |
| `503` | Transient backend issue — retry with exponential backoff |

## Multi-turn

Two ways to continue a conversation — pick one per conversation, don't mix them.

### Resend the history (OpenAI-style)

Append assistant replies to the `messages` array on subsequent calls. The model uses the full conversation as context.

```jsonc
{
  "model": "corebase",
  "messages": [
    { "role": "user", "content": "Top customers this quarter?" },
    { "role": "assistant", "content": "Acme, Globex, Initech." },
    { "role": "user", "content": "And how do they compare to last quarter?" }
  ],
  "stream": true
}
```

### Continue by `conversation_id`

Every response returns a `conversation_id` (as a body field on non-streaming responses, and as the `X-Conversation-Id` header on both). Pass it back with **only the new message** — the server keeps the history, so requests stay small and prompt size doesn't grow with every turn:

```jsonc
// Turn 1 — a new conversation
{ "messages": [{ "role": "user", "content": "Top customers this quarter?" }], "stream": false }
// → { ..., "conversation_id": "abc123" }

// Turn 2 — just the new message
{
  "conversation_id": "abc123",
  "messages": [{ "role": "user", "content": "And compared to last quarter?" }],
  "stream": false
}
```

A conversation belongs to the API token that started it — another token (or another organization) gets a `404`. A continued conversation always stays in the project it started in; `project_id` is ignored on continuation.
