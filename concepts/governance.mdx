title: "Governance"
description: "How CoreBase keeps autonomous agents safe — read-only by default, per-source write opt-in, source scoping, and per-tenant isolation."
---

Autonomous agents are only safe if they're governed. CoreBase puts the guardrails in the **infrastructure**, not in a prompt — an agent can't write where it shouldn't or reach a source it wasn't granted, no matter what it's told.

## Read-only by default

Every source starts read-only.

- **Databases** are read-only at the session level — the connection pool runs with `default_transaction_read_only = on` and a statement timeout. Mutating SQL is rejected by the database itself.
- **REST / GraphQL / SaaS** sources only expose read operations to the agent. Mutating operations (POST/PUT/PATCH/DELETE, GraphQL mutations) are **not produced as tools** unless you opt the connection into writes. The agent never sees a tool it isn't allowed to call — the guard is structural, not a denylist or a prompt.

### Opting into writes

Each API/SaaS connection has an **Allow writes** toggle (off by default). Turn it on and the agent gains the mutating tools for that source — and only that source. Agent nodes in a flow also have their own **Allow writes** switch, so you decide per step.

<Warning>
  Treat write enablement as a deliberate act. Today a source is either read-only or fully write-enabled. Per-write (tool-call level) approval is on the roadmap — until then, keep writes off for anything that runs unattended.
</Warning>

## Source scoping

An agent only ever sees the sources you grant it. In chat you pick sources from the header; in a flow each agent node has a **Sources** list; via the API you pass `source_ids`.

This is enforced structurally — the agent's toolset is built from only the scoped sources, so it cannot "jump" from one system to another (say, from your POS database to your accounting ERP). The tools for the second source were never created for that request, so there's nothing for a prompt to talk it into.

## Per-tenant isolation

Every tenant runs in its own sealed bubble, enforced at the database with **PostgreSQL Row-Level Security** (RLS):

- Each tenant's data, annotations, memories, and connections are scoped by `org_id` and invisible across tenants.
- The application role runs **without** the ability to bypass RLS; isolation holds even if application code has a bug.
- The rare lookups that must span tenants (e.g. routing an incoming webhook to the right tenant) are handled through narrow, audited paths — never a broad bypass.

## Audit

Every meaningful action — running a query, connecting or deleting a source, changing access — is written to the audit log with the actor, target, and timing. Available on Team and Enterprise plans.

## Secrets

- Database DSNs and provider keys are encrypted per tenant (AES-GCM, envelope-encrypted under a master key).
- CoreMCP keeps database credentials on **your** server — CoreBase never sees them.
- SaaS OAuth tokens live in the managed connector layer, not in CoreBase.
- Secrets, prompts, generated SQL, and result rows are never written to logs.

## How the layers stack

| Layer | Guarantee |
|---|---|
| Read-only by default | No writes unless you opt in, per source |
| Source scoping | Agent reaches only the sources you grant |
| Per-tenant RLS | No cross-tenant reads, enforced at the DB |
| Egress posture | Choose where rows are allowed to travel ([egress](/concepts/zero-raw-data-egress)) |
| Audit | Every action is traceable |
